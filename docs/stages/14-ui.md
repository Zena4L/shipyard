# Stage 14 notes: the desktop UI

The engineering record of stage 14: what was built, why it's built that way, what the
kernel and the web view were checked to do, what can go wrong and how that's handled, and
what was left for later stages. For how to *use* it, see [The desktop app](../user/desktop.md)
and [The Docker API](../user/api.md) (Shipyard's own `/shipyard/…` endpoints). The design it
follows is [`docs/design/README.md`](../design/README.md) and its mock,
[`docs/design/shipyard-ui.html`](../design/shipyard-ui.html).

## Outcome

Stage 14 asked for the desktop UI of the design, built on the stage 11 API, **the
observed-traffic map first**, macOS first and Linux by the close ([ROADMAP](../ROADMAP.md),
[FEATURES §14](../FEATURES.md#14-desktop-ui--stage-14)). Its outline was decided on
2026-10-27 (D14-1 to D14-6) and built in steps:

- **14.0** the probes: Tauri 2 on this Mac, `bollard` against the API, compose's
  `depends_on` label (no product code);
- **14.1** the API's new data (a: the map's links and a container's sockets; b: a running
  container's isolation, every volume's size and files);
- **14.2** the app's skeleton: `shipyard-client`, the Tauri shell, the page, the live store;
- **14.3** the map;
- **14.4** the Yard and the inspector (a: views; b: actions and the Run sheet);
- **14.5** the console: logs and a real shell;
- **14.6** the other sections (a: Images; b: Volumes and Networks);
- **14.7** the app on Linux, its service started for it, a Linux UI test and a desktop VM;
- **14.8** the close (a: whole-stage reviews and their fixes; a2: the live numbers the
  real app never had; b: these notes and the proof).

A user can now:

- open **Shipyard.app** on a Mac (`npm run tauri build` in `desktop/`, signed by
  `scripts/macos/sign.sh --bundle`): it starts the VM (or not: Settings), and shows the
  containers, live;
- on Linux, run the app as themselves: it starts their own API service (`shipyard system
  service --ensure`) when nothing answers, and says root's containers aren't shown;
- see **the map**: each compose project left to right from its published ports, declared
  links solid, connections seen in the containers' socket tables but not declared dotted
  orange, a declared link to a stopped target red, dots on the edges with open connections,
  the start order, the networks and volumes and images as overlays, a stopped dependency's
  **Start** in its status line;
- select a container in the **Yard**, the **Map** or the **Manifest**: its inspector says
  what it needs and what needs it (and the YAML to copy for an undeclared connection), its
  image as layers, its networks and mounts, its live CPU and memory against its limit, its
  namespaces, cgroup, PID 1 and user mapping as the kernel has them; Start, Stop, Pause,
  Resume, Restart and Remove (confirmed inline, refused while a running container needs it),
  each with its CLI twin as its tooltip;
- run an image from the **Run sheet** (⌘K), pulled first if missing;
- read a container's **logs** as text and open a **shell** in it (xterm.js, `sh` on a
  terminal) in the console under the view;
- see **Images** as strips of layers (shared layers counted once, families of a base
  coloured alike), **Volumes** as drums (who mounts each, its files, Delete), **Networks** as
  buses (each container's address and veth, the containers that join two);
- see the host's memory in use, each container's CPU and memory, and the monitors' memory,
  read every 2 s while the window is seen.

## Architecture

### The pieces

```
desktop/ (a Cargo workspace of its own: Tauri needs WebKitGTK)
├─ src-tauri/  shipyard-desktop: the core. Tauri 2 commands (src/commands.rs, one list:
│              build.rs declares them, the capability allows each by name), events to the
│              page, one client cached; the stats follower and the console (logs, one
│              shell) by selection number; nothing of the engine
└─ ui/         the page: Svelte 5, TypeScript, Vite. The mock's markup and stylesheet
               (design.css, extracted whole, never edited); store.ts (the live store);
               graph.ts / layout.ts (the map as plain functions); deps.ts, actions.ts,
               layers.ts, storage.ts, usage.ts (each section's model, plain functions)

crates/shipyard-client (in the main workspace, tested on both platforms)
  place.rs     the API's socket (the Mac VM's docker.sock; Linux's own), the trusted shipyard
  api.rs       bollard (negotiated to 1.43) + hyper for /shipyard/…, each version checked
  events.rs    /events read a line at a time (a bad line skipped)
  vm.rs        the Mac VM's phase from host.sock (never docker.sock), its start
  service.rs   Linux: shipyard system service --ensure
  stats.rs, console.rs, run.rs, images.rs, volumes.rs, networks.rs, usage.rs, settings.rs

shipyard system service (stage 11) ── new endpoints, Shipyard's own, each "version": 1
  GET /shipyard/links                      every container, links, entries (shared 1 s)
  GET /shipyard/containers/{id}/sockets    a container's sockets, peers named
  GET /shipyard/containers/{id}/isolation  a running container's namespaces, cgroup, PID 1
  GET /shipyard/volumes                    every volume's size and top level (shared 5 s)
  GET /shipyard/networks/{name}            (stage 11's view, its version beside it: 14.6b)
  GET /shipyard/usage                      the live numbers' counters (shared 1 s)
```

### The data's way

The page asks the core (Tauri's IPC, commands allowed by name), the core asks the client,
the client asks the API's socket. State comes from one place: the container list and
Docker's events (subscribed before the list is read, so nothing between is lost), read
again every 30 s and after each reconnect. Everything the map, the inspector and the
sections draw is made from that and from a few reads polled only while they're shown and
the window is seen: the links every 2 s (the map), the usage every 2 s, the selection's
stats as a stream, the bridges' views while Networks is shown. A window hidden 5 minutes
lets go of every stream (the VM's idle stop can come); shown again, it opens anew.

### The map's links

A link is **declared** (compose's `com.docker.compose.depends_on`, `service:condition:restart`)
or **observed**: an established TCP socket in container A whose remote is container B's
lease and whose mirror (the same four-tuple, reversed) is in B's table; through a published
port, the host's NAT keeps the source port, which confirms it. Each network namespace's
tables are read once, through an init found by PID and start time (re-checked after the
read), never the host's own. A link is counted once, from its client, aggregated per (from,
to, port, protocol): the answer stays small whatever a container opens. Rootless has no
leases (pasta): observed links are said unavailable, declared ones still drawn.

### The web view's rules

No remote content; the CSP `default-src 'self'` (`style-src 'self'`: no inline style, every
run-time value a Svelte `style:` directive, xterm.js's `<style>` elements turned into
constructed stylesheets by `sheets.ts`); fonts bundled (`assetsInlineLimit: 0`); navigation
off the app's own origin refused; every string from a container, an image or a registry
rendered as text (no `{@html}`, `innerHTML` or the like: `verify.sh` greps for them).

## Decisions and why

- **D14-1 Tauri 2** (over Electron, a native toolkit): the design's HTML and SVG carry over;
  a 4 MB `.app`. Its cost: the system web view (WebKit on both platforms here; WebKitGTK's
  quirks on Linux).
- **D14-2 macOS first, Linux by the close**: met in 14.7 (WebKitGTK, the service started for
  the user). Windows stays out (D18); the client's one transport keeps a door open.
- **D14-3 Svelte 5 and TypeScript**: a maintained framework (D19), small output.
- **D14-4 the fix for an undeclared link is YAML to copy**, never an edit of the user's file.
- **D14-5 connections, polled**: socket tables every 2 s, no conntrack accounting (root-only,
  a host sysctl).
- **D14-6 an API client, never the engine in-process**: one path on both platforms; a crash
  of the app can't wedge a container's state. `deny.toml` keeps the engine out of the client.
- **D14.2-1** the client a workspace crate, the shell its own workspace (WebKitGTK isn't in
  the test container), pinned to the main lock's versions (`client-versions.py`).
- **D14.2-2** the VM started on open, a setting turns it off; **D14.2-6** a hidden window lets
  go after 5 minutes.
- **D14.1a-2** an observed link counted once from its client, by a mirror socket;
  **D14.1b-1** isolation is the kernel's, read while it runs, never guessed from the config;
  **D14.1b-2** a volume's walk bounded (200,000 entries, depth 64, 3 s), its listing 200.
- **D14.4b-1/2** Remove stops and removes (`rm -f`), refused while a running container needs
  it; **D14.4b-7** the Run sheet's spec is the mock's alone, the create body the client's.
- **D14.5-1** a real terminal (xterm.js), probed first under the release CSP;
  **D14.5-3** one shell, the selection's, its command the core's.
- **D14.6-2** "Delete N unused" takes every volume no container names; **D14.6b-1** deletions
  by name, one at a time, never forced, the list taken as the confirm opens.
- **D14.7-1** the app shows the user's own engine (rootless on Linux); root's are the CLI's;
  **D14.7-3** the service started by the CLI's own rule (`--ensure`).
- **D14.8a2-1** the live numbers as counters in one read, the page dividing two reads;
  each container's monitor measured by its own ID, its cgroup read without the runtime's
  lock (`peek_stats`).
- **Asked in 14.7:** Tauri's `freezePrototype` off (xterm.js assigns `toString` on a plain
  object, and a frozen `Object.prototype` throws: the blank window); the CSP, the
  capability allowlist, the core's argument checks and text bindings hold.

## Kernel checks

- `/proc/PID/net/{tcp,tcp6,udp,udp6}` are the reader's network namespace's tables, read
  through the container's init (14.0, 14.1a: the e2e reads a connection on both ends; the
  service in a namespace of its own sees none of the host's).
- A connection through a published port keeps its source port across the host's NAT (the
  root e2e connects through the gateway and confirms it).
- `/proc/PID/ns/*` inodes compare across processes; `/proc/PID/task/PID/children` names the
  init's child (else a scan of `/proc` by parent) (14.1b's e2e).
- `statx`'s `STX_MNT_ID` tells a btrfs subvolume or another mount inside a volume, where
  `st_dev` can't (14.1b).
- cgroup v2's `cpu.stat` and `memory.current` are readable by the cgroup's owner without
  the runtime's lock; a removed cgroup reads as missing files (14.8a2's `peek_stats`).
- The Mac's guest has no systemd, so nothing turned on a controller at its cgroup root
  but the `pids` the runtime asks for: its cgroups had no `memory.current`, and `stats`
  said 0B on a Mac since stage 10 (the close's check of `/shipyard/usage` in the VM found
  it). The guest's PID 1 turns on CPU, I/O, memory and processes at boot (`controllers`),
  and the runtime hands down what its parent has.
- `RLIMIT_RTTIME` (or any limit) lower in a desktop session than at a container's start:
  rootless, an exec can't raise it (TLPI §36.2): 14.7's Linux UI test found every exec
  failing; fixed by `within_own`.

## Fuzzing

One new target, `compose_labels` (14.1a): the `depends_on` label's lenient parse, seeds in
`scripts/fuzz-seeds.py`. The close's run: all 19 targets, 300 s each, no crash and no
deprecation in the nightly build's log (`compose_labels`: 5 million runs). `test-linux.sh
--fuzz` now installs nightly only when it's missing: asked every time, rustup fetched its
channel first and failed on this network before any target ran.

## Known limitations (by design, for stage 14)

- Rootless Linux shows no observed links (no leases to name a peer): said in the map's
  status line.
- The live numbers need a container's own cgroup: rootless without delegation shows "—".
- A UDP sender that never connects is invisible to the map (no socket says its peer).
- The app is built from the tree (`npm run tauri build`); no installer yet (stage 15).
- macOS 13.0–13.2's web view has no constructed stylesheets: the shell says so.
- F189: the window can't choose another VM directory.
